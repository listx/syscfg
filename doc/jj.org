#+title: Jujutsu

* Introduction

Jujutsu's main advantage for us is the fact that basically it's rebasing
everything all the time for you (whenever you edit stuff in the history, the
commits on top get rebased). So it saves a couple steps and is generally faster
than using raw Git if you're constantly fixing up your work.

One disadvantage though is that it does not work well with
[[https://github.com/listx/melby][Melby]] (a shell prompt generator which aggressively queries Git for changes),
whenever there is a merge conflict. It's most definitely Melby's fault, not
Jujutsu's, but it's something that we need to fix (we first need to rewrite
Melby to be less complicated, but that's for another day).

** Aliases

~jj git fetch~ updates the trunk but leaves our local work where it was, and
Jujutsu has no built-in command to move that work forward. The ~sync~ alias
fills that gap: it rebases every local line of work onto the upstream trunk in
one step.

The revset picks out what counts as local work. It starts from the visible
heads, drops the ones that are only there because of a remote bookmark (those
are other people's branches, not ours), and adds back our own bookmarks. The
~upstream_trunk()..~ prefix limits this to commits not already on the trunk, and
~-b~ rebases each whole branch, not just the selected heads. The revset doesn't
try to leave out [[revset-aliases][immutable commits]]: if a branch would drag
one along, ~jj rebase~ stops with an error, which is what we want.

~jj sync~ with no arguments rebases onto ~upstream_trunk()~. An argument names
a different destination, as any revset: ~jj sync next~ rebases onto the local
~next~ bookmark, which is handy when stacking work on a branch that isn't the
trunk, and ~jj sync main@u~ names a remote bookmark explicitly (when ~u~ is
the only remote with ~main~, that's the same as plain ~jj sync~). A plain alias
can't do this, because Jujutsu appends any extra arguments to the end of the
expanded command, so ~next~ would land after ~-d upstream_trunk()~ instead of
replacing it. So the alias runs a small shell script through ~jj util exec~,
which receives the extra arguments as ~$1~ and so on (~jj-sync~ fills ~$0~, and
shows up in error messages). The script wraps the argument in parentheses, so
that a compound revset like ~a | b~ stays one unit when it's spliced in front of
~..~. A name that doesn't resolve makes ~jj rebase~ fail with an error, so
nothing moves.

Before rebasing, the script makes Jujutsu track the remote copies of our own
branches, so that they become [[revset-aliases][mutable]] and the rebase can
rewrite them. It counts a branch as ours if we have a local bookmark with the
same name, which is what tracking means in Jujutsu anyway. We need this step
because we create branches and push them with Git, and Jujutsu doesn't track
bookmarks that it only imports from Git. The script reads the bookmark list
with tab-separated fields, because the remote is an empty string for local
bookmarks and would disappear between spaces. It skips the ~git~ pseudo-remote,
which is Jujutsu's view of the colocated Git repo, not a real remote. It also
skips the shared branches, whose remote copies stay immutable anyway. Leaving
them untracked keeps a fetch from moving our local ~develop~ (or ~main~) on its
own. The list of shared branch names appears again in
[[revset-aliases][~shared_remote_bookmarks()~]], and the two must agree.

#+name: aliases
#+begin_src toml
[aliases]
sync = ["util", "exec", "--", "bash", "-euc", '''
if (( $# > 1 )); then
  echo "usage: jj sync [REVSET]" >&2
  exit 1
fi
dest="upstream_trunk()"
if (( $# == 1 )); then
  dest="($1)"
fi
jj bookmark list --all-remotes -T 'name ++ "\t" ++ remote ++ "\t" ++ tracked ++ "\n"' |
  awk -F'\t' '
    $2 == "" { local[$1] = 1 }
    $2 != "" && $2 != "git" && $3 == "false" { untracked[$1] = 1 }
    END {
      for (n in untracked)
        if (n in local && n !~ /^(main|master|develop)$/) print n
    }' |
  while read -r name; do
    jj bookmark track "exact:$name"
  done
exec jj rebase -b "$dest..((visible_heads() ~ remote_bookmarks()) | bookmarks())" -d "$dest"
''', "jj-sync"]
#+end_src

** Revset aliases

Jujutsu refuses to rewrite immutable commits unless we pass
~--ignore-immutable~. Its default set of immutable commits covers the trunk,
tags, and remote bookmarks that we don't track. A tracked remote bookmark is one
linked to a local bookmark of the same name, so in practice that's our own
branch, which we want to keep rewriting and force-pushing. [[aliases][~jj sync~]]
makes sure our branches are tracked.

On top of the default set, we add the branches that everyone shares:
~main~, ~master~, and ~develop~ on any remote. We usually have a local bookmark
for these too (~git clone~ creates one), so tracking alone doesn't tell them
apart from our own branches, but other people push to them, and rewriting their
commits is never what we want.

We used to turn immutability off by setting ~immutable_heads()~ to ~none()~, because the
flag was annoying and Git already requires a force push before rewritten history
leaves this machine. But that only protects the remote, not our local copy. In a
repo whose shared branch is ~develop~, running ~git fetch~ and then
[[aliases][~jj sync~]] produced lots of divergent commits: with nothing
immutable, the rebase was free to rewrite commits that other people had already
pushed, and the next fetch brought back the originals alongside our rewritten
copies.

~upstream_trunk()~ is the trunk that the [[aliases][~sync~ alias]] rebases onto. We
don't use Jujutsu's built-in ~trunk()~ for this, because ~trunk()~ only looks at
~main~, ~master~, or ~trunk~ on a remote named ~origin~ or ~upstream~, and
quietly falls back to ~root()~ when there is none. Some of our repos use other
remote names, and there ~sync~ would rebase everything onto the empty root
commit.

So we look for the ~main~ bookmark on any remote, and fall back to ~master~ if
no remote has ~main~. We use the remote bookmark, not the local one, because
the remote is what we sync against, and a repo might not have a local ~main~ or
~master~ at all. If several remotes have the bookmark (say, a fork and the
project it came from), ~latest()~ picks the newest one, because a rebase onto
more than one destination would create a merge commit. If no remote has either
bookmark, ~upstream_trunk()~ is empty and the rebase fails with an error instead
of guessing.

#+name: revset-aliases
#+begin_src toml
[revset-aliases]
"immutable_heads()" = "builtin_immutable_heads() | shared_remote_bookmarks()"
"shared_remote_bookmarks()" = 'remote_bookmarks(exact:"main") | remote_bookmarks(exact:"master") | remote_bookmarks(exact:"develop")'
"upstream_trunk()" = 'coalesce(latest(remote_bookmarks(exact:"main")), latest(remote_bookmarks(exact:"master")))'
#+end_src

* Ignored files

We symlink ~\~/.config/jj~ to the ~jj~ directory of this repo, so that our
~config.toml~ lives here. But newer versions of Jujutsu also use
~\~/.config/jj~ for their own state: ~repos/~ and ~workspaces/~ hold per-repo
and per-workspace data, kept outside each repo's ~.jj~ directory so that a
cloned repo can't bring along config that we never approved. These directories
then show up in this repo as untracked files. They describe the repos on one
machine, so they don't belong in version control.

Instead of listing those directories, ignore everything in ~jj/~ except
~config.toml~, so that any other state Jujutsu adds there later stays out too.

#+name: gitignore-jj
#+begin_src gitignore
jj/*
!jj/config.toml
#+end_src
