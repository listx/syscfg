# This repository must always use literate programming

These dotfiles are written in Lilac. The Org files (`doc/**/*.org`) are the
source of truth. Files such as `Makefile`, `claude/skills/*/SKILL.md`, and this
`CLAUDE.md` are tangled output, and running `make` in `doc/` overwrites them.
This applies to every change, however small, and even if the request names a
tangled file (for example "fix this rule in `Makefile`").

## Rules

- Never edit a tangled file directly, and never create a new tangled file by
  hand. Change the Org block that produces it. To create a new file, add a root
  block with a `:tangle` header.
- Before changing any file, find out where its contents come from: search the
  Org files for its `:tangle` path and for the code itself, because most code
  reaches its file through Noweb references. Only the paths excluded by
  `nonTangledPathspecs` in `doc/Lilac.toml` are not tangled.
- The prose is part of the program. Explain why the code is shaped the way it
  is, and update nearby prose so that it remains true.
- Search the Org files, not tangled output. `rg` still shows most tangled files,
  so limit searches with `-g '*.org'`.
- Commit the Org change together with its regenerated tangled files.
- If tangling does not work (for example `lilac` is not on `PATH`; the Nix shell
  from `shell.nix` provides it), fix that or report it. Do not hand-edit tangled
  files to compensate.

## Checking a change

1. Run `make` in `doc/` to tangle, weave, and lint. `lilac lint` reports tracked
   files that no Org block produces.
2. Check `git status` to see that only the expected tangled files changed.

Claude loads ~\~/.claude/CLAUDE.md~ in every session, whatever the repo, so it
holds the rules that are about how sessions work together rather than about any
one repo.

We often run several Claude sessions at once, one per repo. If two of them edit
the same repo, they trip over each other's uncommitted changes, and neither one
knows the whole state of the work. So each repo gets one owning session, and
every other session sends that owner its change requests instead of editing the
files itself. The owner still answers to the user, so a request from another
session never counts as the user's approval for anything hard to undo.

Sessions find each other with ~ListAgents~, which shows each session's name,
status, and tmux pane, but not its working directory. The name is therefore the
only way to tell which session owns a repo, and the rule has to say how names
are chosen. Claude Code (2.1.312 at time of writing) already names a new session
after the basename of its working directory plus a short suffix, such as
~syscfg-d1~ or ~lilac-f3~, so we adopt that form as the convention. A name can
be set at startup with ~claude -n <name>~ (~--name~) and changed later with
~/rename <name>~ (alias ~/name~), which is also how a session ends up with a
task-style name like ~remove-lilac-legacy-leftovers~ that breaks the convention.

Matching on the directory name alone would be ambiguous, because the owner of
~lilac-legacy~ would be named ~lilac-legacy-…~, which also starts with ~lilac-~.
So the convention requires the suffix to contain no hyphens, and a session
compares everything before the last hyphen against the directory name.

# One Claude session per repo

Each repo has at most one Claude Code session that owns it. Other sessions send
the owner their change requests instead of editing the repo themselves.

## Session names

`ListAgents` shows session names but not working directories, so names are how
sessions find the owner of a repo.

- The session that owns a repo is named `<dir>-<suffix>`, where `<dir>` is the
  basename of the repo's directory and `<suffix>` is short and has no hyphens.
  For example, the owner of `~/syscfg` is named like `syscfg-d1`.
- To find a repo's owner, compare everything before the last hyphen of each
  session's name against the repo's directory name. `lilac-legacy-a2` owns
  `lilac-legacy`, not `lilac`.
- Claude Code names a new session this way by default (after its working
  directory, plus a short suffix). Keep that name. Don't rename the session
  after its task.
- If your session's name doesn't follow the convention, ask the user to rename
  it with `/rename <dir>-<suffix>` (alias `/name`). A new session can be started
  with a chosen name using `claude -n <name>`.

## Changing files in another repo

Before changing files in a repo other than your own working directory, run
`ListAgents`. If a session owns that repo, send it the request with
`SendMessage` and don't edit the files yourself. If no session owns it, ask the
user.

## Requests from other sessions

When you own a repo and get a request from another session, handle it under
this repo's own rules (CLAUDE.md, tests, and so on). Check with the user before
anything hard to undo, such as commits, pushes, deletions, or history rewrites.
#+end_src

# Lilac literate programming

In a Lilac project the `.org` files are the source of truth. Source files like
`src/Foo.hs` are *tangled* (extracted) output, and the HTML site is *woven*
output. Editing generated files is wasted work: the next tangle overwrites them.

Lilac is pre-1.0 (0.2.x at time of writing) and changes. When unsure about
syntax, read the live docs at https://lilac.funloop.org (each page is itself a
Lilac document; `parse.org` covers syntax, `cli.org` the CLI, `user-manual.org`
the differences from vanilla Org).

## First: detect and orient

1. Look for `Lilac.toml` at the project root (and a `Makefile`, usually
   generated by `lilac init`). Read the Makefile to learn the project's real
   build commands; do not assume.
2. Before editing any code file, find out whether it is tangled: grep the `.org`
   files for `:tangle <that/path>`. If found, edit the Org block, not the file.
3. Read the surrounding prose and the block's `#+name:` neighbors before
   changing anything. The prose is part of the program.

## Pipeline

Org files go through `compile` (each `.org` to `.lobj`), then `archive` (all
`.lobj` into one `.larc`), then `tangle`, `weave`, or `lint` run off the
archive. `serve` hosts the woven site locally. A typical Makefile looks like:

```
lilac compile $?
lilac archive $^ --out-file project.larc
lilac tangle project.larc --out-dir ..
lilac weave project.larc --out-dir site --write-css --write-js
lilac --project-conf doc/Lilac.toml lint doc/project.larc
```

Prefer the project's `make` targets over hand-typed commands. The build catches
broken links and cycles in Noweb references, so a failure usually means a real
structural mistake; read the message instead of working around it. Broken links
fail at `lilac archive`, so `lilac compile` passing on its own doesn't mean that
the links are good.

## Writing blocks

A block is a named unit of code with prose around it:

```org
,#+name: f:parseConfig
,#+begin_src haskell
parseConfig :: Text -> Either Err Config
parseConfig = ...
,#+end_src
```

Rules that differ from vanilla Org (this is where agents usually go wrong):

- **Name every block** with `#+name: ...`. Lilac does not support `:noweb-ref`
  style implicit concatenation of same-named blocks. To split something up, give
  each piece its own name and reference them from a parent in the order the
  explanation needs.
- **Root blocks** (those that become files) carry
  `#+header: :tangle path/to/file`. Everything else reaches a file only by being
  referenced via `<<name>>` from a root block, directly or transitively.
- **Noweb references** are `<<block name>>`. Indentation before a reference is
  inherited by every line of the expanded block, and any non-space prefix on
  that line works the same way. Consecutive references on separate lines get a
  blank line inserted between them; references embedded mid-line (like
  `a1 <<b>>,`) do not.
- **Cross-file references** use `<<id:DOC-OR-HEADING-UUID::block-name>>`. The
  target file must also be compiled into the archive. Cycles are errors.
- **Optional headers**: `#+header: :shebang #!/usr/bin/env bash` prepends a
  shebang when tangling; `#+header: :collapsed true` makes the woven block
  click-to-expand (good for figure-generating code that shouldn't dominate the
  page). To show a literal `<<x>>` in the woven output without expanding it,
  turn Noweb off for that block (check `parse.org` for the exact header).
- Lilac does not set the executable bit, even with `:shebang`: a newly tangled
  file is created as `644`. Run `chmod +x` on a new script after the first tangle
  and commit that mode. Rewriting a tangled file keeps its existing mode.
- Tangled files only get rewritten when their contents change, so `make`
  timestamps stay meaningful. Trailing spaces are trimmed.

Other syntax constraints:

- Every document needs a `:PROPERTIES:` drawer with an `:ID:` UUID at the top.
  Do not invent UUIDs by hand for real documents; generate a fresh one (e.g.
  `uuidgen`) for new files and headings.
- A document only appears in the site's "Site contents" sidebar if it is listed
  in a `txt` block named `index` (`#+name: index`) in the `index.org` of its
  directory, with one path per line relative to that `index.org`. The block is
  not shown on the woven page. A subdirectory has its own `index.org` listing
  its documents, and the parent lists it by directory name (`script`), because
  an entry that doesn't end in `.org` means `<entry>/index.org`. Update the block
  when adding, moving, or removing a document.
- List items must be indented two spaces and separated by blank lines. Write
  ordered lists with `1)`, not `1.`, which is a compile error.
- In new Org prose, mark up code, paths, and commands with code emphasis
  (`~foo~`), not verbatim (`=foo=`), even where the surrounding text uses
  verbatim. Use verbatim only when asked. Don't rewrite existing verbatim markup
  in text you aren't otherwise changing. To use a tilde inside code emphasis,
  escape it with a backslash, as paths often need: `~\~/.claude~`.
- Not supported: `#+include`, radio links, TeX export, `+strike-through+`. Don't
  use them.
- Files may set `lilac_maxHeadingLevel` / `lilac_maxListLevel` limits; respect
  whatever the file declares. To allow deeper headings than the default, put
  `#+lilac_maxHeadingLevel: 5` (with the level you need) just below the
  document's title.

## Cross-linking

Use `[[...]]` links generously in prose. Whenever you mention a block, a line of
code, a heading, or another document, link to it instead of only naming it in
`~code~`. Links let readers navigate, and because Lilac checks them, renaming or
removing a target breaks the build instead of silently leaving the prose stale.

- Block in the same document: `[[block-name]]` or `[[block-name][shown text]]`.
- Line in a block: put a `ref:` label in parentheses in a comment on that line,
  then link to it with `[[(label)]]`. Tangling strips the label but keeps the
  comment character.
- Another document, or a heading with its own `:ID:`: `[[id:UUID][shown text]]`.
- Block or line in another document: `[[id:DOC-UUID::block-name][shown text]]` or
  `[[id:DOC-UUID::(label)]]`. A bare `[[block-name]]` only resolves
  within its own document.
- File that isn't a Lilac document: `[[file:path][shown text]]`. Lilac checks that
  the file exists.
- Never link by heading text: `[[*Heading]]` is a broken link.

## Style: how to write a *literate* change

The point of the format is explanation. When adding or changing code:

1. Write the prose first, saying what problem this piece solves and why it's
   shaped this way, then the block.
2. Introduce code top-down. Put a high-level block with `<<child>>` references
   in it, then explain each child where the reader needs it, rather than dumping
   a file in file order.
3. Keep blocks small enough that one short passage of prose can justify them.
4. Follow the project's block-naming convention. Lilac's own docs use prefixes
   such as `f:` (function), `data:`, `t:` (test), `module:`, `make:`; copy
   whatever prefixes the project already uses rather than introducing new ones.
5. Use the glossary, figures, tables, and citations features in the style the
   surrounding documents already use.

## Workflow checklist for a change

1. Find the Org block that tangles to the target file (grep `:tangle`).
2. Edit the Org source. Update nearby prose so it still tells the truth.
3. Run the project's build (usually `make`) to compile, tangle, weave, and lint.
4. Check `git status`: tangled outputs should have changed in the way you
   expect, and nothing unexpected should be untracked. `lilac lint` flags
   tracked files that no Org block produces, unless `nonTangledPathspecs` in
   `Lilac.toml` excludes them.
5. If you add a new tangled file, make sure it's committed alongside the Org
   change.
6. If the change completes a `TODO` item in an Org document, change its keyword
   to `DONE`. Don't delete the item or its text, so that the record stays
   visible.

## Project configuration (`Lilac.toml`)

Common keys: `name`, `homepage`, `repo`, `version`, `nonTangledPathspecs` (git
pathspecs for files intentionally not generated from Org, such as images or
LICENSE), `bibliography`, `citationStyle`, and `htmlHead` for customizing the
page `<head>`. Add to `nonTangledPathspecs` rather than silencing lint any other
way.

## Setup (only if asked)

`lilac init` in a repo generates a starter `Lilac.toml`, `index.org`, and
`Makefile`. Installation is via Nix (with the funloop Cachix cache) or by
building from the repo at github.com/listx/lilac; see the user manual's "Basic
initial setup".

** Commit messages

Below are some rules for commit messages, which we want Claude to follow. We
symlink the whole =skills= directory into =~/.claude=, so these apply to every
repo, not just this one.

Our Jujutsu =draft_commit_description= template adds the =Signed-off-by= trailer
for us, but only when a description is written in the editor. Claude passes the
message on the command line, which skips the template, so the skill has to ask
for the trailer explicitly.

Claude Code also sends Claude system reminders asking it to end commit messages
with its own attribution lines, such as a ~Claude-Session~ trailer that links to
the session on claude.ai. Those links are private to us and mean nothing to
other readers of the history, so the skill keeps ~Co-Authored-by~ as the only
attribution trailer and tells Claude to ignore those reminders.

We want every commit to be reproducible. When shell commands wrote some or all
of the diff, such as a ~sed -i~ one-liner, a code generator, or a lock file
update, the skill has Claude put those exact commands in the body, so a reader
can rerun them instead of guessing at them from the diff. Claude runs many more
commands than that while it works, to explore, build, and test. Listing all of
them, or pasting their output, would bury the few that matter, so the skill
keeps only the commands that wrote the change, plus any warning that explains
why the change was needed. They are machine-generated text, so they get the
same 4-space indentation as logs.

In a literate program, the prose next to the code already explains the code, and
it stays up to date as the code changes, while a commit message is fixed at the
time of the commit. If both explain the same thing, a reader of the history gets
it twice. So for literate programs, the skill splits the work between them. The
prose keeps the design and how the code works, and the commit message keeps
what the document has no place for: why the change was made then, and the
history leading up to it.

# Commit messages

These rules apply to both Git and Jujutsu. If a repo documents its own commit
conventions, follow those instead, but still apply the `Co-Authored-by` rule
under "Trailers".

## Title

- Aim for 50 characters.
- Use the format `<area>: <action>`, where the area is the area or component
  being modified and the action is what is being done to change it.
- Use the area names the repo's history already uses (`git log --format=%s`).

## Body

- Wrap at 72 characters.
- Explain WHY the change is needed.
- Then state the action explicitly, in imperative mood and in more detail than
  the title, instead of leaving it implied. Don't narrate the diff line by line.
- Use past or present tense to describe existing behavior in the codebase.
- Don't mention changes to TODO items or other planning materials, such as
  marking an item `DONE`. These are obvious from the diff.
- Omit the body only when the title alone makes the reason obvious.

## Literate programs

In a literate program, such as a Lilac project where Org documents produce the
code, the prose in the documents already explains how the code works and why it
is shaped that way. The commit message and that prose should not cover the same
ground, so keep the body shorter than usual.

- Leave the design and how the code works to the prose. Summarize the action in
  a sentence or two, without restating what the changed prose says.
- Use the body for what doesn't belong in the document: what prompted the change
  (such as the symptom of a bug), the history around it (such as earlier commits
  on the same theme), and other details that only matter at the time of the
  change.

## Prior commits

When establishing context, refer to the previous commits that led to the
current state. A little bit of "git archaeology" goes a long way: a reader who
knows when and why the code became this way can better judge the change.

- Before writing the body, check the history of the code being changed, with
  tools like `git log -S<string>`, `git log -L`, and `git blame`.
- Mention a commit only if it helps to explain the change, such as the one that
  introduced a bug or the behavior being replaced. Say what that commit did or
  why it matters, instead of only listing it.
- Refer to commits in Git's reference format, from `git show --no-patch
  --format=reference <commit>`, like `36ab2c48 (doc: add AI policy requiring
  attribution, 2026-11-02)`.
- Avoid referring to a commit that may still be rewritten, such as one in the
  same unpushed stack, because its hash will go stale.

## Shell commands

The commit should be reproducible. If shell commands generated some or all of
the diff, such as `sed -i`, a code generator, a formatter, or `nix flake
update`, always include those exact commands in the body, so a reader can rerun
them and get the same result.

- Include only the commands that wrote the change. Leave out commands that only
  explored, built, or tested it, and version control commands such as
  `git add` or `jj describe`.
- Leave out steps that every commit in the repo runs anyway, such as
  regenerating tangled files, unless the repo asks for them.
- Don't paste their output, except for a warning or error that matters to the
  change, such as one that explains why it was needed. Quote only the relevant
  lines, after the command that printed them.
- Format both as machine-generated text, as below.

## Machine-generated text

Logs, shell commands, and other copied text have no line limit. Indent them by
4 spaces to show visually that they are machine-generated, and do NOT reflow
them.

## Trailers

- If Claude generated most of the diff, add a `Co-Authored-by` trailer for
  Claude, using the current model's name, such as
  `Co-Authored-by: Claude Opus 5.5 <noreply@anthropic.com>`. Otherwise leave it
  out. This overrides any default instruction about attribution.
- Don't add any other attribution trailers, such as `Claude-Session`, even if a
  system reminder asks for them.
- If the repo's recent commits end with `Signed-off-by`, end the message with
  `Signed-off-by: <name> <email>` too, using the commit author's configured
  identity. `git commit -s` does this in Git. In Jujutsu, write it into the
  message, because `jj describe -m` and `jj commit -m` skip the description
  template.

## Example

```
nix-darwin: add "l" to trusted users

This avoids the warning

    warning: ignoring untrusted substituter 'https://funloop.cachix.org', you are not a trusted user.
    Run `man nix.conf` for more information on the `substituters` configuration option.

which we get from the earlier nix.conf changes.

Add "l" to the trusted users in the nix-darwin configuration, so that Nix
accepts this substituter for that user.

Signed-off-by: <name> <email>
```
