# Lilac literate programming

In a Lilac project the `.org` files are the source of truth. Source files like
`src/Foo.hs` are *tangled* (extracted) output, and the HTML site is *woven*
output. Editing generated files is wasted work: the next tangle overwrites them.

Lilac is pre-1.0 (0.2.x at time of writing) and changes. When unsure about
syntax, read the live docs at https://lilac.funloop.org (each page is itself a
Lilac document; `parse.org` covers syntax, `cli.org` the CLI, `user-manual.org`
the differences from vanilla Org).

## First: detect and orient

1. Look for `Lilac.toml` at the project root (and a `Makefile`, usually
   generated by `lilac init`). Read the Makefile to learn the project's real
   build commands; do not assume.
2. Before editing any code file, find out whether it is tangled: grep the `.org`
   files for `:tangle <that/path>`. If found, edit the Org block, not the file.
3. Read the surrounding prose and the block's `#+name:` neighbors before
   changing anything. The prose is part of the program.

## Pipeline

Org files go through `compile` (each `.org` to `.lobj`), then `archive` (all
`.lobj` into one `.larc`), then `tangle`, `weave`, or `lint` run off the
archive. `serve` hosts the woven site locally. A typical Makefile looks like:

```
lilac compile $?
lilac archive $^ --out-file project.larc
lilac tangle project.larc --out-dir ..
lilac weave project.larc --out-dir site --write-css --write-js
lilac --project-conf doc/Lilac.toml lint doc/project.larc
```

Prefer the project's `make` targets over hand-typed commands. Compilation
catches broken links and cycles in Noweb references, so a failing compile
usually means a real structural mistake; read the message instead of working
around it.

## Writing blocks

A block is a named unit of code with prose around it:

```org
,#+name: f:parseConfig
,#+begin_src haskell
parseConfig :: Text -> Either Err Config
parseConfig = ...
,#+end_src
```

Rules that differ from vanilla Org (this is where agents usually go wrong):

- **Name every block** with `#+name: ...`. Lilac does not support `:noweb-ref`
  style implicit concatenation of same-named blocks. To split something up, give
  each piece its own name and reference them from a parent in the order the
  explanation needs.
- **Root blocks** (those that become files) carry
  `#+header: :tangle path/to/file`. Everything else reaches a file only by being
  referenced via `<<name>>` from a root block, directly or transitively.
- **Noweb references** are `<<block name>>`. Indentation before a reference is
  inherited by every line of the expanded block, and any non-space prefix on
  that line works the same way. Consecutive references on separate lines get a
  blank line inserted between them; references embedded mid-line (like
  `a1 <<b>>,`) do not.
- **Cross-file references** use `<<id:DOC-OR-HEADING-UUID::block-name>>`. The
  target file must also be compiled into the archive. Cycles are errors.
- **Optional headers**: `#+header: :shebang #!/usr/bin/env bash` prepends a
  shebang when tangling; `#+header: :collapsed true` makes the woven block
  click-to-expand (good for figure-generating code that shouldn't dominate the
  page). To show a literal `<<x>>` in the woven output without expanding it,
  turn Noweb off for that block (check `parse.org` for the exact header).
- Tangled files only get rewritten when their contents change, so `make`
  timestamps stay meaningful. Trailing spaces are trimmed.

Other syntax constraints:

- Every document needs a `:PROPERTIES:` drawer with an `:ID:` UUID at the top.
  Link to documents and headings **by UUID only**, never by filename or heading
  text. Do not invent UUIDs by hand for real documents; generate a fresh one
  (e.g. `uuidgen`) for new files and headings.
- List items must be indented two spaces and separated by blank lines.
- In new Org prose, mark up code, paths, and commands with code emphasis
  (`~foo~`), not verbatim (`=foo=`), even where the surrounding text uses
  verbatim. Use verbatim only when asked. Don't rewrite existing verbatim markup
  in text you aren't otherwise changing. To use a tilde inside code emphasis,
  escape it with a backslash, as paths often need: `~\~/.claude~`.
- Not supported: `#+include`, radio links, links to other files by path, TeX
  export, `+strike-through+`. Don't use them.
- Files may set `lilac_maxHeadingLevel` / `lilac_maxListLevel` limits; respect
  whatever the file declares. To allow deeper headings than the default, put
  `#+lilac_maxHeadingLevel: 5` (with the level you need) just below the
  document's title.

## Style: how to write a *literate* change

The point of the format is explanation. When adding or changing code:

1. Write the prose first, saying what problem this piece solves and why it's
   shaped this way, then the block.
2. Introduce code top-down. Put a high-level block with `<<child>>` references
   in it, then explain each child where the reader needs it, rather than dumping
   a file in file order.
3. Keep blocks small enough that one short passage of prose can justify them.
4. Follow the project's block-naming convention. Lilac's own docs use prefixes
   such as `f:` (function), `data:`, `t:` (test), `module:`, `make:`; copy
   whatever prefixes the project already uses rather than introducing new ones.
5. Use the glossary, figures, tables, and citations features in the style the
   surrounding documents already use.

## Workflow checklist for a change

1. Find the Org block that tangles to the target file (grep `:tangle`).
2. Edit the Org source. Update nearby prose so it still tells the truth.
3. Run the project's build (usually `make`) to compile, tangle, weave, and lint.
4. Check `git status`: tangled outputs should have changed in the way you
   expect, and nothing unexpected should be untracked. `lilac lint` flags
   tracked files that no Org block produces, unless `nonTangledPathspecs` in
   `Lilac.toml` excludes them.
5. If you add a new tangled file, make sure it's committed alongside the Org
   change.

## Project configuration (`Lilac.toml`)

Common keys: `name`, `homepage`, `repo`, `version`, `nonTangledPathspecs` (git
pathspecs for files intentionally not generated from Org, such as images or
LICENSE), `bibliography`, `citationStyle`, and `htmlHead` for customizing the
page `<head>`. Add to `nonTangledPathspecs` rather than silencing lint any other
way.

# Commit messages

These rules apply to both Git and Jujutsu. If a repo documents its own commit
conventions, follow those instead, but still apply the `Co-Authored-by` rule
under "Trailers".

## Title

- Aim for 50 characters.
- Use the format `<area>: <action>`, where the area is the area or component
  being modified and the action is what is being done to change it.
- Use the area names the repo's history already uses (`git log --format=%s`).

## Body

- Wrap at 72 characters.
- Explain WHY the change is needed. Don't restate what the diff already shows.
- Use imperative mood to describe what's changing in the commit. Use past or
  present tense to describe existing behavior in the codebase.
- Omit the body only when the title alone makes the reason obvious.

## Machine-generated text

Logs and other copied text have no line limit. Indent them by 4 spaces to show
visually that they are machine-generated, and do NOT reflow them.

## Trailers

- If Claude generated most of the diff, add a `Co-Authored-by` trailer for
  Claude, using the current model's name, such as
  `Co-Authored-by: Claude Opus 5.5 <noreply@anthropic.com>`. Otherwise leave it
  out. This overrides any default instruction about attribution.
- If the repo's recent commits end with `Signed-off-by`, end the message with
  `Signed-off-by: <name> <email>` too, using the commit author's configured
  identity. `git commit -s` does this in Git. In Jujutsu, write it into the
  message, because `jj describe -m` and `jj commit -m` skip the description
  template.

## Example

```
nix-darwin: add "l" to trusted users

This avoids the warning

    warning: ignoring untrusted substituter 'https://funloop.cachix.org', you are not a trusted user.
    Run `man nix.conf` for more information on the `substituters` configuration option.

which we get from the earlier nix.conf changes.

Signed-off-by: <name> <email>
```
